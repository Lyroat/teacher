# outline-highlight-draft

把「根据大纲框架写某一集的标绿稿」固化成流程的 Skill。输入是教研已确认的大纲框架或内容简案，输出是一篇 1170—1230 字、结构固定、可直接进石墨流转的讲解稿。

## 适用边界：只写，不审

**这个 Skill 只负责“写”，不负责“审”。**同事说“审核一下这篇标绿稿”“帮我看看这篇有什么问题”，要走 `science-fact-check`，不是这里。

判断依据是**动词**，不是产物类型——请求里出现“标绿稿”三个字，不代表该用这个 Skill。

`scripts/check_highlight_draft.py` 只是写完之后的**格式合规自检**（字数、模块齐备、结构），它不做科学性把关，不能当审核结论交付给用户。这条最容易混，值得单独记住。

## 文件构成

```
outline-highlight-draft/
├── SKILL.md                         199 行   路由 + 红线，每次触发都读
├── docs/
│   ├── output-contract.md           271 行   产物长什么样（字数、结构、模块规则）
│   ├── writing-style.md             141 行   语言和知识怎么组织
│   ├── interaction-design.md         95 行   【互动探索】怎么设计
│   └── self-check.md                157 行   45 条交付前检查清单
└── scripts/check_highlight_draft.py 657 行   格式自检脚本
```

分层的依据是**加载时机**：SKILL.md 每次触发都会被读进上下文，`docs/` 只在真正做那一步时才读。所以 SKILL.md 只放“判什么模式、去哪找输入、走哪个阶段、哪些绝对不能碰”，具体“怎么写”全部下沉到 docs。

字数规则只在 `docs/output-contract.md` 的「字数」一节定义一次，SKILL.md 和脚本都只引用不复述——以前多处各写一套数值，改一个地方就会漏改别处。

## 五种任务模式

动手前先判定模式，并在回复第一句说明。判错模式比写得不好后果严重得多。

| 模式 | 触发说法 | 允许改动的范围 |
| :--- | :--- | :--- |
| A 新生成 | “写 E11 标绿稿” | 全文新写 |
| B 结构性改写 | “重写关键问题2”“这段逻辑不对” | 指定部分，其余不动 |
| C 语言润色 | “这句拗口”“太书面了” | 只改措辞，不动知识点和结构 |
| D 格式修复 | “引号不对”“表格缺一行” | 只改格式，一个字的知识内容都不动 |
| E 只检查不修改 | “看看字数够不够”“有什么问题” | 不写文件，只输出问题清单 |

C、D 模式下遵守**最小改动原则**：不在用户指出范围内的句子，一个字都不改，不顺手优化没被问到的段落。理由很实际——同事下一步大概率要逐句核对改动，顺手改的地方会让核对成本翻倍。

模式判不准就直接问，不要按 A 模式重写全文。用户说“改一下”而拿回一篇新稿，等于删掉了他此前所有的手工修改。

## 四个阶段

### Phase 1 提取与框架检查

从框架里提取本集的标题、主线问题、关键问题链、每个关键问题下的知识点 bullets、互动探索位置、思维方式标签。

然后在对话里输出一个简短的【框架检查】块（不写进文件），报四项风险：知识点覆盖、认知顺序、科学表述、标绿稿可写性。

以下情况要先停下来确认，不能自己拍板：主线问题缺失或有多个候选、知识点与关键问题对不上、框架内容明显超出 1230 字容量、互动探索被拆散后会导致逻辑断裂。

### Phase 2 确定讲解结构

整体节奏：

```text
引入（≤1min）→ 知识精讲（约 9min，含互动探索）→ 大总结（≤1min）
```

这里有一条同事容易意外的规则：**关键问题之间的顺序跟随框架，但关键问题内部知识点的顺序自己定。**

框架 bullets 的排列是教研梳理知识时的记录顺序，标绿稿是要连着读出来的口播稿，两者对顺序的要求本来就不同。哪个顺序读起来更顺、因果链更完整就按哪个写，不需要事先请示，但要在交付说明里写一句为什么这么排。**没重排也要先在心里过一遍**，不能因为框架给了顺序就默认它最优。

边界是：只调顺序，不增删知识点，不跨关键问题搬运（跨问题搬运属于结构调整，要先说明再动）。

### Phase 3 生成稿件

按输出契约写正文。默认存到：

```text
01-outputs/<主题>/04-大纲/E<集数>/<主题>_E<集数>_标绿稿.md
```

### Phase 4 交付前检查

先按 45 条清单自查，再跑脚本，最后给交付说明。

## 产物形态的硬性要求

### 字数

目标 1200 字，硬性范围 1170—1230 字。

统计方式是**正向白名单**：只统计明确列为计入的区域——各关键问题正文，以及互动探索表格**之后**的解释文字。主标题、元信息行、【引入】、【互动探索】表格、【大总结】、趣味拓展全部不计入。

用白名单而不是“排除已知例外、其余全算”，是因为反向方式每加一个新模块都得记着补例外，漏一个就静默算错。

一个字怎么数：**标点计入**（逗号句号引号破折号都算 1 字），汉字逐字计，连续的字母或数字串按 1 字计（「2019」算 1 字），空白不计，Markdown 语法符号先剥掉。手工核对能和脚本对上。

### 必备结构

```markdown
# <主题> E<集数> 标绿稿

主线问题：...

## 【引入】
## 关键问题1：<框架原文>
## 【互动探索】      ← 表格形式，含预测题
## 关键问题2：<框架原文>
## 【大总结】
```

### 几个容易踩的细节

- 关键问题小标题必须**逐字**保留框架原文。`⭐` 和 `【看到现象】` 这类标签留在标题里，但**正文一个字都不读这些标签**。标签是给教研看的思维方式标记，正文要做的是落实标签对应的思维动作，而不是写一句“接下来我们来追问原因”。
- 【大总结】200—250 字，只总结标了 `⭐` 的关键问题，不引入新知识点，不做泛泛升华。判断标准是“这句话在说什么”而不是“有没有某个词”——“保护土壤，从现在做起”不含“升华”二字，但它就是升华。
- 单段正文不超过 180 字，全文问题句不超过 8 个。
- 引入禁止用“今天我们来学习……”开头，且结尾的悬念必须能被正文第一段自然接住。
- 趣味拓展**不是必需的**。每篇最多一处、不超过 100 字，写不出自然贴合主线的就不写，不要为了有这个模块硬凑。

## 互动探索的抽离测试

这是实操中最常被违反的一条。【互动探索】是**可抽离的插入模块**，不是正文的一部分。

检验方法：把表格整块删掉，剩下的正文必须独立讲清四件事——

1. 观察到了什么现象
2. 为什么会这样
3. 这说明了什么
4. 和主线问题什么关系

四件事有任何一件只存在于表格里，就说明互动模块替代了正文讲解，必须把知识搬回正文。

典型的失败长相是：写着写着把机制讲解搬进了表格的「预期发现」行，正文只剩下引出实验和总结实验，知识本身没讲。

配套的禁止项：正文里不许出现“刚才的探索告诉我们……”“你刚才看到……”这类句子，删掉表格后它们会失去指向。脚本能自动查这类表述。

正文和表格讲同一件事**不算重复**——表格是让学生自己做一遍，正文是把结论讲清楚，两者都要完整。

## 脚本的三档输出

```bash
python3 scripts/check_highlight_draft.py <draft.md>

# 逐字核对关键问题标题与框架是否一致
python3 scripts/check_highlight_draft.py <draft.md> --framework <框架.md>

# 输出删掉互动表格后的正文，供人工做抽离测试
python3 scripts/check_highlight_draft.py <draft.md> --interaction-test
```

输出分三档，这个分层是为了避免“一堆告警里混着真问题”：

| 档位 | 含义 | 典型内容 |
| :--- | :--- | :--- |
| **FAIL** | 必须修好才能交付 | 字数越界、缺模块、关键问题编号重复或倒序、超 180 字的段落、问题句超 8 个、互动表格缺必备行、趣味拓展超量或标记不配对、出现 HTML 高亮代码 |
| **WARNING** | 需人工判断，可保留但要说明理由 | 大总结字数偏离建议范围、标题与框架不一致、互动表格缺「题型」行 |
| **INFO** | 只是统计数字，不需处理 | 分项字数、小标题数、问题句数，以及脚本查不了的项 |

「题型」行只判 WARNING 不判 FAIL，是因为它是后加的要求，早于该要求的旧稿普遍没有。

脚本明确查不了、必须人工核对的四项：知识覆盖、科学准确性、语言质量、知识点顺序是否通顺。

**使用陷阱**：反向同步时不要传 `--framework`。以标绿稿为准去改框架的场景下，标题本来就该不一致，传了只会得到一堆无意义的告警。

## 45 条自查清单的分级

`docs/self-check.md` 的 45 条分 11 个小节，每条都打了权限标签：`[自动修正]` 30 条，`[必须确认]` 26 条（有几条按情况兼具两种）。

分界线是**会不会改变知识内容或科学表述**：

- 引号半角改全角、拆长段、改错别字 → 直接动手
- 知识点删减、科学结论调整、跨关键问题搬运 → 只报告问题和建议改法，不动原文

拿不准时按 `[必须确认]` 处理。

## 四条安全规则

这几条都是踩过坑之后加的。

**不静默改科学结论。**科学准确性高于框架忠实度——框架里的科学表述有问题，不能因为“框架就是这么写的”照抄。但反过来也不行：发现问题不得在稿子里悄悄改掉，要在【框架检查】里标出、说清风险、给出建议措辞、等确认。静默修正会让框架和标绿稿的知识内容对不上，而且没人知道是谁改的、为什么改。

需要逐条核对的六类高风险内容：具体数字、历史案例、科学家姓名和实验、多步机制、绝对化表述、安全健康环境类。

**不默认覆盖已有文件。**目标路径已存在且用户没明确说“覆盖”时，新建 `_v2` 版本文件，或者停下来问。已有文件里往往有手工改过、不在对话记录里的内容，覆盖掉就找不回来。宁可多建一个文件让人自己删。

**改稿必须给改动清单。**格式是「原文 → 改后 + 理由」，另外要列出**没动**的模块，让人知道改动边界在哪。只说“已优化语言”“调整了表述”不算清单，用户无法据此核对。顺手改的地方也要报——没报的改动等于藏起来的改动。

**字数不达标默认只诊断、不自行改。**这条优先于“把字数改进范围内”。严禁这个流程：

```text
超字数 → 从正文中间删句 → 重新统计 → 直接交付
```

标绿稿的知识是“现象—机制—结论”的解释链，机械删句会让稿子形式上通过字数检查，但科学逻辑已经断裂：现象保留而原因被删、“因为……所以……”只剩一半、代词失去指向。这比单纯超字数更严重，因为人类教研只看最终稿不一定能发现被删掉的桥梁。

契约里列了七类不得优先删除的「逻辑桥梁」，并规定了固定的压缩顺序：

```text
删除重复句 → 压缩修辞 → 合并同义句 → 缩短非关键例子
→ 压缩框架外拓展 → 最后才考虑删除整段
```

## 怎么用

Skill 装在 `~/.claude/skills/`，走自动触发。说“帮我写《地球》E11 标绿稿”“根据大纲框架写 E5 标绿稿”就会进来，不需要斜杠命令。`~/.codex/skills/` 下有一份同步的镜像供 codex 用。

新同事上手建议的阅读顺序：

1. `SKILL.md` 通读一遍，建立全局印象
2. `docs/output-contract.md` 的「字数」和「必备结构」两节
3. `docs/self-check.md` 全表

`docs/writing-style.md` 和 `docs/interaction-design.md` 可以等实际动手写的时候再翻。

## 14 条核心红线

SKILL.md 末尾的红线清单，出现冲突时以它为准：

1. 不得遗漏本集主干知识点，除非用户明确同意删减。
2. 不得改写或缩窄关键问题原意。
3. 不得省略关键问题原文；每个关键问题必须以 H2 小标题独立呈现。
4. 不得为了趣味补充大段框架外知识。
5. 不得输出 HTML 背景标绿、红色 span 或其他可视化高亮代码。
6. 必须写表格形式【互动探索】模块，且包含预测题。
7. 【互动探索】不得破坏正文连续性；互动模块不能替代正文讲解。
8. 必须写【大总结】，且只总结标有 `⭐` 的关键问题对应的重点知识。
9. 全文问题句 8 个以内，单段正文不超过 180 字。
10. 不得为了达到字数范围而机械删句。
11. 不得静默修改框架里的科学结论。
12. 不得默认覆盖已有文件。
13. 修改已有稿件时必须给出改动清单；顺手改的地方也要报。
14. 本 Skill 不承担审稿职责；用户要求审核标绿稿时改用 `science-fact-check`。
