# 大纲标绿稿生成

> **适用边界：本 Skill 只负责“写”，不负责“审”。**
>
> 用户说“审核标绿稿”“审阅/检查/挑错/把关标绿稿”“帮我看看这篇标绿稿有什么问题”时，一律改用 `science-fact-check` Skill，不要进入本 Skill，也不要用 `scripts/check_highlight_draft.py` 代替审核。
>
> 判断依据是**动词**，不是产物类型。“标绿稿”这三个字出现在请求里，不代表该用本 Skill。
>
> `scripts/check_highlight_draft.py` 只是本 Skill 写稿交付前的格式合规自检（字数、模块齐备、结构），它**不做科学性审核**，不能作为审核结论交付给用户。

## 核心任务

根据主题的大纲框架或内容简案，为指定集次生成可进入大纲/石墨流转的“标绿稿”。标绿稿不是完整逐字稿，而是目标约 1200 字、硬性范围 1170—1230 字的精炼讲解稿。

字数只统计可朗读的正文讲述内容。**具体计入与不计入范围以 `docs/output-contract.md` 的「字数」一节为唯一准绳**，本文件不另行定义。

## 任务模式判定

动手前先判定属于哪种模式，并在回复开头一句话说明。模式决定改动范围，判错模式比写得不好后果更严重。

| 模式 | 触发说法 | 允许改动的范围 |
| :--- | :--- | :--- |
| A 新生成 | “写标绿稿”“生成 E几标绿稿”“根据大纲框架写” | 全文新写 |
| B 结构性改写 | “重写关键问题2”“调整讲解顺序”“这段逻辑不对” | 指定部分的结构和内容，其余不动 |
| C 语言润色 | “这句拗口”“语言再顺一点”“太书面了” | 只改措辞和句子切分，不动知识点、不动结构、不动字数量级 |
| D 格式修复 | “引号不对”“标题格式错了”“表格缺一行” | 只改格式，一个字的知识内容都不动 |
| E 只检查不修改 | “看看字数够不够”“检查一下格式”“有什么问题” | 不写文件，只输出问题清单 |

**最小改动原则**：C、D 两种模式下，凡是不在用户指出范围内的句子，一个字都不改。不要顺手优化没被问到的段落——用户下一步很可能要逐句核对改动。

模式判不准时，直接问用户一句，不要按 A 模式重写全文。用户说“改一下”而你交回一篇新稿，等于删掉了他们此前所有的手工修改。

## 使用资源

按任务读取以下文档：

- 生成或大改标绿稿前，读取 `docs/output-contract.md` 和 `docs/writing-style.md`。
- 生成、修改或检查【互动探索】时，读取 `docs/interaction-design.md`。
- 交付前，读取 `docs/self-check.md`。
- 有本地 Markdown 文稿路径时，交付前运行 `python3 scripts/check_highlight_draft.py <draft.md>`。仅限本 Skill 写稿后自检使用；不得用于响应用户的“审核标绿稿”请求。

旧的通用讲稿规则不得覆盖本 Skill 的标绿稿规则。若其他写作规范与本 Skill 冲突，以 `docs/output-contract.md`、`docs/interaction-design.md` 和 `docs/self-check.md` 为准。

## 输入定位

1. 确认主题与集次，例如《地球》E2。
2. 优先读取用户指定文件。用户点名了文件，就用那个文件，即使你觉得另一个更新。
3. 若用户未指定文件，按优先级寻找：
   - 更详细的内容简案，例如 `01-outputs/<主题>/03-内容简案/*内容简案*.md`
   - 大纲框架，例如 `01-outputs/<主题>/03-内容简案/*大纲框架*.md`
   - 其他包含 12 集结构、主线问题、关键问题和知识点的课程框架文件
4. 如果同时存在大纲框架和内容简案，优先使用内容简案；同时用大纲框架核对本集标题、主线问题、关键问题原文和顺序。
5. 如果项目内存在 `02-产品研究/学生科学知识误区_权威调研汇总.md`，且能检索到与本集主线相关的误区，可读取相关段落作为引入素材；不要为了使用误区而偏离主线问题。

同一类输入常并存多个版本，选错会让整篇稿子建立在废弃内容上。选版本的顺序：用户指定的无条件优先 → 认定稿（“定稿”“终版”“已确认”）优先于过程稿（“草案”“初稿”“讨论稿”“WIP”） → 同为正式版本时取版本号较高的，看不出高低时取修改时间较新的。**不得凭“更新”选过程稿**，新改的草案可能正是被否掉的那版。判断不了就列出候选文件和修改时间让用户点一个，不要默认挑一个开写。

交付时必须列出实际用到的输入文件完整路径，一个不漏。

## Phase 1：提取与框架检查

从输入中提取本集：

- 标题
- 主线问题
- 关键问题 / 问题链
- 每个关键问题下的知识点 bullets
- 互动探索/交互探究的位置、问题、操作方式、预期发现
- 科普与拓展素材
- 思维方式培养目标，尤其是关键问题中的 `【】` 标签

写作前在对话中简短输出框架判断，不写入正文文件：

```text
【框架检查】
标题：
主线问题：
关键问题链：
知识点覆盖风险：✅/⚠️/❌
认知顺序风险：✅/⚠️/❌
科学表述风险：✅/⚠️/❌（⚠️/❌ 需逐条列出）
标绿稿可写性：通过/需确认
互动探索位置：已有/建议新增/需确认
```

出现以下情况时，先向用户说明并等待确认：

- 主线问题缺失或有多个候选。
- 本集知识点与关键问题无法对应。
- 框架内知识点明显超出 1230 字容量，需要删减。
- 互动探索与前后知识点被拆散后会导致逻辑断裂。

**科学表述风险**：科学准确性高于框架忠实度，但**发现框架的科学结论有问题时不得在标绿稿里悄悄改掉**——在【框架检查】里标出、说清风险、给出建议改法，等确认后再动。需要逐条核对的高风险内容（数字、历史案例、科学家与实验、多步机制、绝对化表述、安全健康类）和处理流程见 `docs/writing-style.md`「科学表述风险」。

## Phase 2：确定讲解结构

整体节奏：

```text
引入（≤1min）
→ 知识精讲（约9min，包含互动探索）
→ 大总结（≤1min）
```

知识精讲内部通常是：

```text
互动探索（约2min，偏前或跟随框架位置）
→ 主体知识精讲
```

结构原则：

- 关键问题本身的**数量、原文和先后顺序**跟随大纲框架或内容简案，不重新发明一套问题链。
- 每个关键问题必须用框架原文作为 H2 小标题，格式为 `## 关键问题N：<框架原文>`。
- 若框架原文含 `⭐` 或 `【】` 标签，必须保留，并在正文中落实其思维动作。
- 若关键问题包含“科学家怎么知道”“为什么”“如何推断”等方法维度，正文必须讲到证据、方法或推理过程。
- 逐条对照关键问题下的 bullets，主干知识不得遗漏。
- 需要调整关键问题之间的顺序时（例如互动探索必须整体移动才能形成闭环），在交付时说明理由。
- **关键问题内部的知识点顺序自己定。**框架 bullets 的排列是教研梳理知识的记录顺序，不一定是最好的口播顺序；哪个顺序更通顺、因果链更完整就按哪个写，不需要事先请示，但要在交付说明里写一句为什么这么排。**没重排也要先过一遍**，不能默认框架的顺序最优。可重排的典型情况和边界（只调顺序、不增删知识点、不跨关键问题搬运）见 `docs/writing-style.md`「主动找更好的讲解顺序」。

## Phase 3：生成或修改标绿稿

按 `docs/output-contract.md` 输出结构生成正文，按 `docs/writing-style.md` 处理语言和知识讲解，按 `docs/interaction-design.md` 处理【互动探索】。

写作时特别注意：

- 标绿稿整体都是将进入标绿大纲的内容；不要输出 HTML 背景标绿、红色 span 或“这里标绿”之类编辑说明。
- 引入必须紧扣主线问题，并在正文第一段被自然接住。
- 关键问题之间要有真实逻辑过渡，不用空泛流程提示或不存在的转折。
- 陌生术语、仪器、效应、理论、方法名优先先描述现象、结构或用途，再给出名称。
- 【互动探索】必须是可抽离的插入模块；删除表格后，前后正文仍然能顺畅连读。
- 大总结只总结重点知识，不做泛泛升华，不引入新知识点。
- H2 小标题保留框架原文里的 `⭐` 和 `【】` 标签，但**正文一个字都不读这些标签**。标签是给教研看的思维方式标记，不是口播内容。正文要做的是落实标签对应的思维动作，而不是提到标签本身。

### 保存与覆盖

默认保存为 `01-outputs/<主题>/04-大纲/E<集数>/<主题>_E<集数>_标绿稿.md`，用户指定路径或版本号时以用户要求为准。

**默认不覆盖已有文件。**目标路径已存在时，只有用户明确说了“覆盖”“直接改这个文件”“更新原文件”才写入；否则先读已有文件，若是本集既有稿而用户意图是重写，新建 `..._标绿稿_v2.md` 并在回复里说明原文件未动；判断不了就停下来问，不要先写了再说。

已有文件里往往有用户手工改过、不在对话记录里的内容，覆盖掉就找不回来。宁可多建一个文件让用户自己删。

## Phase 4：交付前检查

本阶段只在本 Skill 写完或改完稿之后执行，是写稿方的格式合规自检，不是对外交付的审核报告。

1. 按 `docs/self-check.md` 自查。清单里标 `[自动修正]` 的项直接改；标 `[必须确认]` 的项只报告问题和建议改法，不动原文，等人类教研确认后再改。拿不准时按 `[必须确认]` 处理。
2. 有本地文件路径时运行：

```bash
python3 scripts/check_highlight_draft.py <draft.md>
```

需要逐字核对关键问题标题与框架是否一致时，加 `--framework`：

```bash
python3 scripts/check_highlight_draft.py <draft.md> --framework <框架或内容简案.md>
```

`--framework` 是可选项，不传就跳过标题核对。**反向同步时不要传**——即以标绿稿为准去改框架的场景下，标题本来就该不一致，传了只会得到一堆无意义的告警。

需要验证正文能否脱离互动模块独立成篇时，加 `--interaction-test`：

```bash
python3 scripts/check_highlight_draft.py <draft.md> --interaction-test
```

该选项会输出删掉【互动探索】表格后的正文，供人工判断。它只提供材料，不单独判定通过与否。

3. 脚本输出分三档，按档处理：
   - **FAIL**：必须修好才能交付。
   - **WARNING**：需人工判断，可以保留，但保留时要在回复中说明理由。
   - **INFO**：只是统计数字，不需要处理。
4. 若脚本报字数不在范围内，默认只诊断并给出建议，不自行删句或补写；按 `docs/output-contract.md` 的「字数不达标时的处理流程」执行。其他 FAIL 项先修正再交付。
5. 文件中不写框架检查、自查表、推荐理由等中间过程。
6. 修改已有标绿稿时（模式 B、C、D），交付说明里必须给出改动清单（原文 → 改后 + 理由）并列出未改动的模块。只说“已优化语言”不算清单；顺手改的地方也要报。格式见 `docs/self-check.md`「修改已有稿件时的改动清单」。
7. E 模式（只检查不修改）下**不写任何文件**，只输出问题清单：每条给出位置、问题、建议改法，不给出改好的新稿。

## 核心红线

1. 不得遗漏本集主干知识点，除非用户明确同意删减。
2. 不得改写或缩窄关键问题原意。
3. 不得省略关键问题原文；每个关键问题必须以 H2 小标题 `## 关键问题N：<框架原文>` 独立呈现。
4. 不得为了趣味补充大段框架外知识。
5. 不得输出 HTML 背景标绿、红色 span 或其他可视化高亮代码。
6. 必须写表格形式【互动探索】模块，且包含预测题。
7. 【互动探索】不得破坏正文连续性；删除表格后，前后正文必须仍能顺读，且仍独立讲清了知识本身。互动模块不能替代正文讲解。
8. 必须写【大总结】模块，且只总结标有 `⭐` 的关键问题对应的重点知识。
9. 全文问题句数量控制在 8 个以内，单段正文不超过 180 字。
10. 不得为了达到字数范围而机械删句。字数超限只触发诊断和建议，删减需人类教研确认。
11. 不得静默修改框架里的科学结论。发现问题要报出来等确认，不能在稿子里直接改掉。
12. 不得默认覆盖已有文件。目标路径已存在且用户未明确要求覆盖时，新建版本文件或停下来问。
13. 修改已有稿件时必须给出改动清单；顺手改的地方也要报。
14. 本 Skill 不承担审稿职责；用户要求审核标绿稿时改用 `science-fact-check`。
